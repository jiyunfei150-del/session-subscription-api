会话订阅接口手册

用户在问数会话里问了几轮、满意后点「订阅」：后端用模型配置里的结果模型，把整个会话整理成一份订阅说明（Markdown）。订阅中心保存它，每次到点把它当作问题交给智能问数重新取数。

接口 POST /subscription/summary 订阅单位 整个会话 返回 同步 JSON 更新 2026-10-13
●后端状态：代码已合入 dev，尚未上预发。上预发后与智能问数 /ask/stream 同一服务地址，可联调时另行通知。

对接步骤

多轮问到满意→点「订阅」生成说明→用户确认并选频率→到点回放问数
  1. 用户点「订阅」：调 POST /subscription/summary，请求体带这次问数用的会话号 session_id。不论按钮在哪条回答下，订阅的都是整个会话。
  2. 确认页：用返回的 title 作订阅名，渲染 markdown 给用户看；warnings 非空时逐条提示，不拦截。用户选好执行频率后，保存 title 和 markdown。
  3. 到点执行：把保存的 markdown 当问题提问，用法同现有订阅推送。

通用约定

项说明
身份user_id 必填，与调问数接口时传的是同一个值。只能订阅自己发起的会话。
项目project（项目名）或 project_id，传法与问数接口相同，数字或字符串都行。只整理该项目下的轮次。
整理范围整个会话。用户中途换话题算一个新任务：取过数的任务都纳入订阅，各自以最后的说法为准，被否定的口径写进「不要做」；问规则、闲聊这类没取数的问答不纳入。会话超过 30 轮时只看最近 30 轮。
模型模型配置页「结果与分析模型」的主模型，失败自动转兜底模型。
数据只读会话记录，不查数仓，不需要查数凭据。说明里不带任何历史结果数值，每次执行都重新取数。
鉴权与问数接口相同：服务端开启口令时带请求头 X-Api-Token。
耗时一次模型调用，通常 10–60 秒。主模型不可用、转兜底模型时会更长，前端请求超时建议设为 6 分钟；经网关转发时注意网关的读超时。

生成订阅说明

POST/subscription/summary

同一会话可以多次调用，每次重新生成。

请求
{
  "session_id": "1001",
  "project_id": 31,
  "user_id": "<user_id>"
}
字段必填说明
session_id是问数时用的会话号，字符串或数字，最长 128 字符
user_id是会话发起人
project / project_id二选一同问数接口
响应
{
  "session_id": "1001",
  "project": "猎鱼达人3D",
  "title": "渠道首充与次留",
  "markdown": "# 渠道首充与次留\n\n每次执行时，按注册渠道看近 7 日首充率和新增用户次留……\n\n## 一、各注册渠道首充率\n…\n\n## 参考 SQL\n…",
  "turns": [0, 1, 2, 3],
  "warnings": [],
  "elapsed_ms": 18342
}
字段说明
title订阅名，15 字左右，可直接作订阅列表的标题；与 markdown 首行一级标题相同
markdown订阅说明全文，结构见下一节。保存它，到点原样当 query 用
turns整理进去的轮次序号（0 起）；没取数的问答不在其中
warnings确认前要让用户知道的事，字符串数组，可能为空，见提醒
elapsed_ms生成耗时（毫秒）

订阅说明的结构

说明写给一个看不到原会话的问数助手，所以每一项都写全称，时间写成相对执行日的规则。

段落内容
# 标题同 title
首段一句话订阅问题：离开原会话也能直接问的完整问句
## 时间规则每次执行取哪段时间（如"执行日前 7 个完整自然日"）、统计粒度。原问题是固定区间（如"9 月"）时改为滚动规则并注明
## 口径与筛选指标及口径要点、人群与筛选、维度
## 交付内容要哪些表、哪些图，结论关注什么
## 一、任务名…会话里有多个取过数的任务时，每个任务一节，节内用 ### 时间规则 ### 口径与筛选 ### 交付内容，代替上面三段
## 不要做用户否定过、改口前的口径
## 待确认会话里没确认的口径；没有写"无"
## 参考 SQL可能没有。生成时实际交付、且与最终口径一致的语句，由系统原样附上；日期是当时的窗口，执行时按时间规则替换

确认页可以让用户改正文。「参考 SQL」段建议保留：删掉后每次由问数重新写语句，口径可能和用户满意的那次不一样。

markdown 示例（单个任务）
# 各注册渠道近7日首充率

每次执行时，统计执行日前 7 个完整自然日内各注册渠道活跃用户的首充率，按首充率从高到低排列。

## 时间规则
- 每次执行取：执行日前 7 个完整自然日（不含执行当天）
- 统计粒度：7 天整段汇总

## 口径与筛选
- 指标：首充率 = 窗口内首充用户数 / 窗口内活跃用户数，首充以 is_first_pay=1 判定
- 人群与筛选：窗口内的活跃用户（当日有登录）
- 维度：注册渠道（dim_user.reg_channel）

## 交付内容
- 表：各注册渠道首充率，按首充率降序
- 图：各注册渠道首充率柱状图
- 结论：首充率排名，指出明显偏低的渠道

## 不要做
- 不按登录渠道分组
- 不用"当日有付费"作付费口径，统一按首充

## 待确认
- 无

## 参考 SQL
生成订阅时实际交付的语句，口径以此为准；语句里的日期是当时的窗口，每次执行按「时间规则」换成当次窗口。

```sql
-- S3 各注册渠道首充率（生成时窗口 2026-10-06 ~ 2026-10-13）
SELECT r.reg_channel, COUNT(DISTINCT CASE WHEN p.is_first_pay=1 THEN p.user_id END)/COUNT(DISTINCT p.user_id) AS first_pay_rate FROM dw.dws_user_pay_d p JOIN dw.dim_user r ON p.user_id=r.user_id WHERE p.log_date >= '2026-10-06' AND p.log_date < '2026-10-13' GROUP BY r.reg_channel ORDER BY first_pay_rate DESC
```

提醒 warnings

由程序按会话记录判定，不经模型。文字可直接展示，不需要按内容分支处理；用户看过后仍可订阅。

可能出现的提醒意味着
整个会话没有取过数（只有文字回答）……会话里都是问规则、解释类问答，订阅后每次也只有文字
「某任务」没有交付方案记录，参考 SQL 不含这部分……这部分每次由问数按说明重新写语句
「某任务」交付方案不完整：……查询语句记录不全，参考 SQL 可能缺
交付语句 S… 过长或被截断，未附进参考 SQL个别语句没附
要求「……」：未完成 / 换了口径，未经用户确认 / 降维、只完成一部分 / 待用户选口径没完全按用户原话的口径做，这类口径会写进说明的「待确认」
「某任务」仍有 N 条未解决的口径缺口……有数据缺口没解决，订阅结果可能同样缺
用户对第 N 轮「……」点了踩某个任务的最后一条回答用户不满意，建议提示确认
会话较长，只整理了最近 30 轮更早的轮次没进订阅
结果模型没有点名参考语句……参考 SQL 只附了各任务最近一次执行的语句

错误

生成订阅说明的错误走 HTTP 状态码，响应体 {"detail": "…"}，文字可直接展示（422 时 detail 是校验明细数组）。

状态码含义
401口令错误
403没带 user_id，或会话不属于该用户
409本会话在该项目下还没有任何问答（也可能是 project 传错了）
422请求体不合法（如缺 session_id 或为空、超长）
502结果模型生成失败（主模型和兜底都没成），稍后重试
